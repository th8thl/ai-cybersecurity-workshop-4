Exercise 2 · Introduction

Finding weaknesses in source code

Learn before the exercise

What is SAST?

Static Application Security Testing examines source code for potential security weaknesses.

What happens in this lab

  • Bandit and Semgrep read the two files in review_examples/.
  • They produce warnings with rule IDs and source locations.
  • The script saves their results as JSON, a structured text format.

What a warning means

  • The code matches a rule worth investigating.
  • Open the cited source to check the input and safeguards.
  • A completed scan with zero warnings can still miss a weakness.
The portal does not need to receive requests for a static scan.

Learn before the exercise

Bandit and Semgrep · What are they?

Two scanners can notice different things in the same source.

Bandit

  • A security scanner for Python code.
  • Its built-in checks flag Python operations that may be unsafe.
  • Example: B301 flags a call that deserializes pickle data.

Semgrep

  • A scanner that matches code against rules.
  • This workshop supplies the rules in scripts/semgrep.yml.
  • One rule flags the example attachment path operation.
We compare the code behind the warnings, rather than counting every warning as a separate bug.

Learn before the exercise

What does CWE mean?

Common Weakness Enumeration gives recurring kinds of security mistakes a shared name.

Our two categories

  • CWE-502 · Deserialization of Untrusted Data.
  • The importer reads an uploaded Python object format that can have unsafe effects.
  • The repaired importer accepts JSON and validates the ticket fields.

Our second category

  • CWE-22 · Path Traversal.
  • The downloader can construct a file path from a supplied name without the needed boundary check.
  • The repaired code confines the path and checks its ticket attachment record.
A CWE names the weakness category. A CVE identifies a specific published vulnerability. These workshop examples have no assigned CVE.

Learn before the exercise

Read a scanner warning before accepting it

The rule ID, location, and message tell you where to begin.

Bandit JSON fields

  • test_id identifies the check, such as B301.
  • filename and line_number point to source.
  • issue_text describes the concern.

Semgrep JSON fields

  • check_id identifies the configured rule.
  • path and start.line locate the code.
  • extra.message explains the rule match.
Two alerts about importing and calling pickle may describe one underlying weakness.

CodeQL is another static analyzer, run by GitHub on your repository.

How do we score a reviewer?

Compare claims against a shared answer key and the source the reviewer covered.

Known issues

  • Confirmed · the report identifies a known issue and source supports it.
  • Missed · it covered the file but omitted a known issue.
  • Count each distinct known issue once per reviewer.

Other outcomes

  • False alarm · source evidence contradicts the claimed issue.
  • Not reviewed · the file was outside the review or coverage is unclear.
  • Keep unresolved claims separate until you verify them.
A low alert count can mean fewer false alarms, more misses, or less coverage. Check the evidence before concluding.
